最初にプロジェクトへ小さな機能を追加しました。しかし、大規模な変更にはより堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるため、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。Issue を使って機能を作り、コードの妥当性と機能の動作を確かめ、最終的にプロジェクトへ正常にマージします。

> [!NOTE]
> 機能の作業を続ける間は、同じセッションを使います。通常、扱うファイルの種類ごとに異なるセッションや PR を作成しますが、ここでは中心となる概念に集中できるよう手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub Issue から新しいエージェント セッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで機能を実装します。
- コードをレビューします。
- ブラウザー キャンバスで機能を手動検証します。

機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成します。その後、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者はカテゴリーやパブリッシャーでゲームを絞り込む必要があります。バックログの Issue には機能が記載されていますが、複数カテゴリーを組み合わせる方法などは、コーディング前に合意が必要です。Plan モードで決定し、範囲を限定した実装を Autopilot に任せます。

## 背景

AI コーディング エージェントを開発フローに導入しても、基本は変わりません。むしろ、さらに重要になります。多くの開発者は、次のような手順で作業します。

1. 必要な作業の詳細が記載された Issue を開きます。
2. 構築する内容を計画します。
3. コードを作成してレビューします。
4. テストを実行し、コードを検証します。
5. 新機能を手動で検証します。
6. pull request (PR) を作成します。
7. コードレビューと継続的インテグレーション (CI) が成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを調整したものです。

この標準的なアプローチを守ることで、AI が生成したコードが要件を満たし、人が作成したコードと同じ審査プロセスを通るようにできます。

## セッション モード

**セッション モード**は、エージェントの自律性を制御します。プロンプト フィールド下のドロップダウンから設定し、いつでも変更できます。

- **Interactive**: ユーザーとエージェントが共同で作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが完全に自律して作業し、ユーザーの入力を待たずにコードを書き、テストを実行して反復します。

Plan モードで開始し、計画をレビューしてから Autopilot で実装します。

## Issue からセッションを開始する

開始する前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys リポジトリ フォルダーを選び、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに含まれる Issue なので、新しく作成する必要はありません。
2. **New session** を選択し、更新済みの `main` を基点とする **new working tree** を選びます。

    ![GitHub Copilot app の Issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード セレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` の実行を依頼します。ターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョン マネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画によって、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したので、Copilot は機能リクエストをすでに把握しています。次の内容を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を Issue の受け入れ条件と照らし合わせます。カテゴリーとパブリッシャーによる絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数カテゴリーをどう組み合わせるか、一致するゲームがない場合はどうするかなど、未確定の動作について話し合います。

計画には、プロジェクトの既存ツールを使った lint、単体テスト、E2E テスト、型チェックが含まれるべきです。範囲はフィルター機能の実装とテストに限定します。品質ワークフローを終えてから PR を作成します。計画を承認する前に必要な変更を依頼し、後の検証のために Issue の URL と合意した明確化事項を控えます。

## Autopilot を明示的に承認する

計画に問題がなければ、**Approve and implement this plan** または使用中のバージョンで表示される同等のオプションを選択します。承認するとモードも切り替わると決めつけず、現在のモードを確認してください。モード表示が **Autopilot** になっていることを確認します。

Copilot が実装を開始します。計画に沿って処理を進め、コードを生成してテストを実行しながら反復します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があります。先に計画をレビューしてください。依存関係の不足やポートの競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。自分で起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードも、他のコードと同じようにマージ前にレビューします。コードを確認し、サイトを実行して問題がないか検証します。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリーとパブリッシャーの組み合わせを含め、結果を Issue と承認済みの明確化事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、単体テスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はプレビューをビルドして配信し、ローカル サーバーを再利用する場合があります。テスト対象が前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くか確認しましょう。前と同じようにアプリを起動し、ブラウザー キャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザー キャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリーを選択し、結果が一致することを確認します。フィルターを解除してからパブリッシャーを選択し、その結果も確認します。
4. カテゴリーとパブリッシャーを組み合わせ、結果を Issue と承認済みの計画と照合します。複数カテゴリーがサポートされる場合は、合意した組み合わせ動作を確認します。
5. ゲームが一致しない組み合わせを試して空の状態を確認します。フィルターを解除またはリセットし、全件が再表示されることを確認します。
6. 確認が終わったら、次のプロンプトでこのセッションが起動した開発サーバーを停止します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンのためにセッションを保持する

まだフィルター機能の PR を作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを維持します。次はフィルター機能のコードにカスタム指示を適用し、その後スキルと QA の改善を追加して、レッスン 8 でまとめて PR を作成およびマージします。開発サーバーを停止したらセッションをアイドル状態にして構いません。次のレッスンで同じセッションに戻ります。
